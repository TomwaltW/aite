# 任务 AA3 — 守卫拦过 10 次不该拦的，而它只有 10 条回归钉着行为

## 背景：这轨是从哪来的

守卫（`.claude/hooks/guard_bash.py`）到 __TODAY__ 为止，在台账里留下了 **10 次误拦**
（X1 1 次、Y1 2 次、Y2 2 次、Z1 3 次，外加总管这一侧 2 次）。Z2 把它们归成了四类，
写在 `core/crates/app/tests/guard.rs` 的模块头里：

| 撞到的写法 | Z2 的判定 | 标准绕法 |
|---|---|---|
| `AITE_RELOCK=1 …` | 设计如此 | 没有。改 `.claude/**` 只能出补丁脚本给人跑 |
| `find … -delete` / `-exec` | 设计如此 | `ls` 列出来 + 点名 `rm -f` |
| Read / `cat` 守卫自身或 `settings.json` | 设计如此 | 没有。开场自检要撞的就是这一条 |
| 命令里出现受保护路径的**字面量**（`git add <那个路径>`） | 固有代价 | `git add -u` |
| `cargo fmt --all`（写模式，碰冻结面） | 固有代价 | 逐个文件 `rustfmt --edition 2024 <file>` |
| heredoc 正文里有配不平的引号 / 中文引号 | 固有代价 | 改用 Write 工具落文件 |
| heredoc 正文被判「不透明载荷」 | 固有代价 | 同上 |
| 正文里的 `**` 反向匹配到死探针 | 已收窄（V6 (3a) 删了那条探针） | 不再复现 |

**这张表有个问题：它是从会话经历里归纳的，没有一行是黑盒实测出来的。**
「固有代价」这四个字是判断，不是测量结果。而守卫本体只有 **10 条回归**
（`tests/guard.rs`）钉着行为 —— 一个拦过 10 次不该拦的东西，行为边界基本是没被钉住的。

**所以本轨的第一件事不是改守卫，是量它。** 能不能改、改哪里，是量完之后才有的结论。

## ⚠️ 这一轨的硬约束：你读不到要改的那个文件

`.claude/**` 在守卫的 `PROT_PATHS` 里（`readable=False`，**读和写都拦**）。
Read / `cat` 守卫自身会被当场拦下，这是设计如此，不是可以绕的东西。

**技术上存在一条绕法，本轨明令禁止**：编译后的测试代码用 `std::fs` 读文件不受守卫管辖
（守卫只管工具调用），所以一条临时测试可以把守卫源码整个 `println!` 出来。
**不许这么用。** 守卫拦读的意图就是「agent 不要照着源码去改守卫」，用测试当读取通道
是在绕意图，不是绕实现。Z2 用过这个机制，但它只 `println!` 了 hook 命令**那一条字符串**、
用完就删，并在回执里写明了 —— 那是取一个它必须知道的锚点，不是 dump 源码。**边界在这儿。**

**你可以做的**：喂 payload、看退出码和错误消息。`tests/guard.rs` 的 `run_guard()`
就是干这个的（`python3 <守卫脚本>` + 一份 PreToolUse payload → 退出码）。
守卫的错误消息里带着它自己的判定（如 `blocked: 该操作触碰受保护面 <路径>（读取位置）`、
`（不透明载荷）`），**那些字符串就是你能拿到的全部信息**。黑盒能量多细，就量多细。

## 要干的活

### ① 黑盒把行为边界量出来（本轨的主体，别急着改）

对上面那张表的**每一行**，设计 payload 去复现，并把触发条件收窄到最精确的那一条。
要回答的是「**到底什么触发了它**」，不是「大概是这类东西」。举例（不限于这些）：

- **「命令里出现受保护路径的字面量」** —— 是任何位置都拦，还是只在判不出读/写的位置拦？
  `git add .claude/settings.json` 与 `echo .claude/settings.json` 与
  `# 注释里提到 .claude/settings.json` 三者一样吗？路径出现在 heredoc 正文里呢？
- **「heredoc 正文里配不平的引号」** —— 单引号、双引号、中文引号各自如何？
  正文里只有引号而没有任何受保护路径时还拦不拦？
- **「不透明载荷」** —— Z2 已经证伪了「正文太长」这个归因（3.7KB 与 32KB 纯中文都放行，
  带受保护路径字面量的短命令当场被判）。那**真正的判据是什么**？
  是「受保护路径 + 判不出读/写位置」这一条吗？把它精确到能写成一句话。
- **`cargo fmt --all`** —— 拦的是「`--all` 这个词」，还是「它会碰冻结面」这个推断？
  `cargo fmt -p aite` 呢？`cargo fmt --check --all`（只读模式）呢？
  **只读模式还拦的话，那是一条可以收窄的真误拦。**

**每一条都要有：payload 原文 + 退出码 + 错误消息逐字。** 量出来和 Z2 那张表不一致的地方，
**以你量的为准**，并在回执里点出来（那张表是归纳的，你的是测的）。

### ② 把量出来的边界落成回归

现在 10 条回归覆盖的是「该拦的拦、该放的放」几个大类。**你量出来的每一条精确触发条件，
都该有一条测试钉着** —— 尤其是那些「按直觉该放行、实际被拦」的格子：
它们是后面每一轮都会再撞一次的坑，钉住了至少下一个人一眼能看到判据。

- 用 `run_guard()` 那套机制，别自己造第二套；
- **双向断言**：该拦的拦 + 该放的放。只断前者是恒真断言（范本见 Z2 那条）；
- 测试名要说人话，读名字就知道钉的是哪一格。

### ③ 收窄：能改就出补丁，改不了就说清为什么

**这一条是有条件的，不是必须交付。** 判断标准：

- ① 量出来的结果里，**有没有一条是「真误拦」**——即按守卫自己的意图就不该拦、
  且触发条件精确到能定位判据？（候选：`cargo fmt --check`、heredoc 正文参与路径扫描）
- 如果有，而且你能在**不读源码**的前提下把锚点定位到可以精确替换的程度 ——
  出补丁脚本，形状照 `review/z2-guard-patch.py`。
- **定位不到就别写。** 一份锚点靠猜的补丁比不写更坏：它会在「整份拒写」和
  「改错地方」之间赌，而赌输的代价是守卫静默失效。

**改不了的话，② 就是本轨的全部交付，这完全合格。** 把「量到了什么、为什么改不了、
真要改需要什么」写清楚，下一轮（或总管直接动手）就有依据了。

### ④ fail-closed 这条底线，全程不许动摇

守卫的第一性质是**失效时必须停下来喊人，不能静默放行**（2026-09-12 真踩过：hook 执行失败
是非阻塞放行且不报警，整场守卫静默失效，没有任何人知道）。
**任何收窄提案都要先过这一关**：收窄之后，守卫失效时还是 fail-closed 吗？
不是的话，那条提案直接废掉，不管它能省多少麻烦。

   **没有那个变量就当场拒绝执行**。
5. `cargo fmt --all` 会被守卫拦（本轨正好要研究这一条）——改用
   `rustfmt --edition 2024 crates/app/tests/guard.rs`。
6. **落盘无残留**：探测用的临时文件、临时测试收尾前清干净，`git status` 复核。
