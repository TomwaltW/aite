## 10. 契约缺口（给 T0 / T0.1）

① **`wecom_v1()` 的 `outbound_rate_per_min`**：T0 原卡没给。本轨取 **30** —— 原卡 / plan §2C 的平台事实是「每会话 30 条/分钟」，
取别的值要么放过平台会拒的量（>30），要么无端压低吞吐。注意语义差别：契约字段注释写「adapter 自己令牌桶」、没说作用域；
企微是**每会话**滑动窗口（本包按会话计），飞书的 60 是全局令牌桶。建议 T0 在 `wecom_v1()` 取 30，并在字段注释里写明「作用域 / 算法由 adapter 定」
（或者 T0.1 加一个 `outbound_rate_scope` 枚举）。仅是取值对齐，**不需要新字段**就能先落地。

② **`EdgeStatus` 没有「备用」位**：主备里的备机今天 `Connected()=false`，`!status` 只能显示「离线」，与「真掉线」混在一起。
开放通道绕不过：`EdgeStatus` 是 edge 回报 core 的结构，没有 `raw` / `meta` 这类开放字段，core 也无从区分。
**判断：是缺口，但不紧急** —— P1 的主备是「人工起两台」的少数部署，备机显示离线不会导致错误行为（core 只是不往这台发），
值得进 T0.1 而不是阻塞 T0：形状建议 `EdgeStatus.platform_role`（枚举 `PRIMARY` / `STANDBY` / `UNKNOWN`），或最小化成 `bool platform_standby`；
edge 侧由 `wecom.Platform.Standby()` 供数（DD8 的 status 源接它）。钉钉若也有「单连接」约束可共用。

除这两条外无别的缺口（`NormalizedEvent.quote`、`EventKind::Reaction`、`wecom_v1()` 能力位、`WecomConfig` 都是 T0 已计划的，本轨没绕着造）。
